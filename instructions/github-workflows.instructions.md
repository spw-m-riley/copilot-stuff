# GitHub Actions workflow guidance

## Guidance

- Prefer existing repository patterns, reusable workflows, and trusted actions before adding bespoke job graphs or large inline shell scripts.
- Keep triggers, path filters, concurrency, caching, and matrix expansion intentional so workflows only run when they should.
- Run `actionlint` against all changed workflows and fix any issues it finds.

## Baseline

- Pin every `uses:` reference to a full commit SHA and include a version comment for readability unless a more specific local rule documents an allowed exception; do not commit mutable refs such as `@v4`, `@main`, or `@latest` by default.
- Set `permissions` explicitly. Start from `contents: read` at the workflow level and widen scopes only for the jobs that need additional access.
- Prefer OIDC or another short-lived federated auth path for cloud access instead of long-lived cloud credentials stored as repository secrets when federation is available.
- When a workflow uses shared resources or can hang on external systems, pair intentional `concurrency` settings with explicit `timeout-minutes` so stalled runs fail predictably.
- Default `actions/checkout` to `fetch-depth: 1`; only fetch full history when release, tagging, or other history-aware steps actually need it.
- For protected deployments, use GitHub `environment` rules with the right reviewers, branch restrictions, and secrets; include post-deploy smoke checks and keep rollback steps clear and testable.
- Use artifacts to pass built outputs and publish test, coverage, or security results when downstream jobs or reviewers need them; set `retention-days` intentionally and keep artifact names and paths exact.

1. [GITHUB-ACTIONS] When a packaging job writes build artifacts into a subdirectory (e.g. `iac/tf/.assets-web-app`) and then uploads them with `upload-artifact`, the `path` in the upload step must match the exact directory the job wrote to — not a parent directory. Verify staging paths end-to-end across package and deploy jobs; a mismatch (e.g. uploading `artifact-staging/iac/tf/.assets-*` when the job staged to `artifact-staging/.assets-*`) silently produces empty artifacts and causes downstream apply jobs to fail with missing plan files.
2. [GITHUB-ACTIONS] Always verify which workflow or run actually deployed a commit before inferring the pipeline from repository files or historical patterns - the same commit can be deployed through a different active workflow than the legacy config suggests

[GITHUB-ACTIONS] When a repository contains both `.gitleaks.toml` and `.github/gitleaks.toml`, never assume a GitHub Action and the local `gitleaks` CLI will use the same config by default; explicitly set the workflow's config path to the intended file so CI and local scans enforce the same rule set

[GITHUB-ACTIONS] When a workflow job runs `docker build` against a Dockerfile that `COPY`s generated build output (for example `dist/`), do not split the Docker build onto a fresh runner unless the plan explicitly provides artifact handoff; otherwise keep the prerequisite build step in the same job so the copied directory actually exists

[GITHUB-ACTIONS] When a reusable workflow gets deployment credentials from its own job-level `environment`, do not declare those same credentials as required `workflow_call` secrets - GitHub validates required `workflow_call` secrets at the call site, where environment secrets are unavailable, so the run fails before any job steps start
24. [GITHUB-ACTIONS] When fixing a CloudFormation or SAM deployment workflow, prefer auth and deployment patterns from a direct CloudFormation/SAM reference repo over Terraform workflow examples - the shared OIDC concepts transfer, but the deployment-role contract and step shape differ in ways that matter
25. [GITHUB-ACTIONS] When Matt asks to improve workflow readability, include substantive structure or control-flow cleanup in the workflow itself; SHA pinning, timeouts, and other hardening-only changes are not enough unless he explicitly scopes the task to hardening - this workflow-readability PR initially missed the main readability problem in `terraform-deployment.yml`
26. [GITHUB-ACTIONS] Prefer first-party artifact actions like `actions/download-artifact` over custom `gh run download` shell loops when combining artifacts inside a workflow run - Matt explicitly called out custom artifact-download Bash as unnecessary workflow complexity
27. [GITHUB-ACTIONS] In Lloyds-Wealth/SPW repositories, look for org shared reusable workflow repos named `github-workflows-*` before keeping or adding local workflow logic; DevOps prefers consumers to use those shared workflows where the repository contract fits - Matt clarified this org convention during the SPW Fact Find workflow refactor
28. [GITHUB-ACTIONS] When a job is unexpectedly skipped even though its own `if:` is true and its direct `needs:` all succeeded, suspect transitive skip propagation: a skipped ancestor (e.g. a push-only `preflight` that is skipped on `workflow_dispatch`/tags) propagates a skip through an intermediate `always()` job to downstream jobs that do not themselves use `always()`. Fix the skipped ancestor (make it run and succeed) rather than the downstream `if:` - in `aws-referral-report-generator` this is why dispatch deployments silently skipped while push-to-develop deployed, and chasing the job `if:` ref checks (#155/#156/#157) was a red herring
29. [GITHUB-ACTIONS] When diagnosing non-obvious GitHub Actions `if:`/`needs:`/skip behaviour, build a minimal isolated probe workflow that reproduces only the suspected mechanism, push it to a feature branch (trigger on `push` to that branch since `workflow_dispatch` only resolves workflows on the default branch), read the per-job results, then delete the probe - this empirically proves the mechanism before merging a real fix instead of guessing. Matt explicitly praised this probe-workflow approach
30. [GITHUB-ACTIONS] You can validate a deployment workflow's own logic on a feature branch by dispatching it with `gh workflow run <file> --ref <branch>` (the run uses that branch's copy of the workflow), but a source-ref gate job will fail on a non-default branch and skip downstream deploy jobs by design; use this to confirm upstream jobs (e.g. preflight/build) form a clean chain, and rely on isolated probes for the positive downstream-runs proof
